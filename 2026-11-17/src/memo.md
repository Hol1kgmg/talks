## 結論

WebMCP なら、画面と同じ状態をもとにツールを仕分けられる。既存のフロントエンドはそのままで、足すのはつなぐ部分だけ

## 構成

1. なぜ WebMCP か: 概要、他の手段との比較、ユーザー親和性と AI フレンドリーの両立
2. 作る土台はもうそろっている（型・目視確認・テスト・実行環境。Kitesurf は実行環境として触れる）
3. 既存のフロントエンドにつなぐ: hooks・API などの既存実装は話さない。`routesFor` → `navigate` ツール → `registerTool`、Zod の1つの定義から `inputSchema` と `safeParse` を作る
4. 状態でツールを仕分ける: 状態を型（guest / admin の判別共用体）で表し、行き先とツールの入力をそこから導く。guest ならツールを登録しない。出し分けは認可ではない
5. まとめ

コードは説明用の抽象的な例。times#143 は実装例として脚注で触れる。デモは times のブラウザアプリを動かすので、状態はデモと同じ guest / admin の2つにする

## 時間配分

仮実装のまま方針どおりに作ると約13分になり、10分を超える。以下の配分で10分に収める（各スライドの TODO コメントにも目安を書いている）。

| スライド | 目安 |
|---|---|
| タイトル・自己紹介 | 60秒 |
| WebMCP とは（図解） | 75秒 |
| AI にサイトを使わせる方法（3ブロック） | 45秒 |
| 両立（図） | 30秒 |
| 土台 | 30秒 |
| つなぐ部分 | 45秒 |
| Zod（3枚目のコードを具体化） | 75秒 |
| 状態の型 + 行き先の一覧（1枚にまとめる） | 60秒 |
| 状態が変わればツールも変わる | 60秒 |
| デモ（録画） | 60秒 |
| まとめ | 30秒 |
| section 3枚 | 各10秒 |
| **合計** | **600秒** |

縮めるための方針:

- 状態の型と routesFor を1枚にまとめる
- デモは録画にする
- 土台は名前とアイコンだけを見せて流す
- 手段の比較と両立は主張が重なるので、それぞれ軽くする
- 「出さないものは出さない」を削除しても、「ツールの出し分けは認可ではない」はまとめに一言残す
